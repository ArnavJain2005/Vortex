Read this first, then `Docs/TRACK3_PLAN.md` (current step, what is verified, what is blocked).

## Mission

A strong, honest, reproducible submission for the **Samsung PRISM XR Hackathon Challenge 2026, Track 3:
"Path Finder: Trajectory Estimation Under Sensor Degradation"**. Deadline **22 Nov 2026, 11:59 PM IST**
(confirmed by the organisers' FAQ, 17 Nov). Solo entry (Arnav Jain); full time from 20 Nov.

**The official task (organisers' slides and FAQ of 17 Nov 2026):** estimate a 6-DoF trajectory from a
**degraded IMU only** (any EuRoC MAV or TUM-VI sequence, degraded with the organisers' `degrade_imu.py`;
gravity alignment unknown). Output `estimated_trajectory.txt`: `timestamp tx ty tz qx qy qz qw`,
seconds, exactly one pose per input IMU row; never append rows. Survive rising noise, bias and scale
drift, spikes, stuck runs, duplicated rows and dropouts (dropouts are physically MISSING rows); the last
5 s keep their timestamps but the sensor values are invalid (the official script writes exact zeros):
dead-reckon through them. Waypoints are hidden and never an input. Budget: 8 MB peak measured at
**algorithm / heap level** (not process RSS), <= 20 ms compute per second of IMU, single thread,
offline. **Python only** (`main.py`; `main.cpp` is not accepted). Batch, non-causal processing is
allowed (read the whole file, smooth, then write). Scoring: SE(3) Umeyama alignment, then ATE (evo)
against hidden ground truth; efficiency 40 (memory 20, runtime 20), trajectory 60 (waypoints 30,
blind 5 s 20, dropouts 10).

**Our approach: velocity witnesses.** No pretrained network. The IMU's own physics gives drift-free
hints about velocity (V1 stillness, V2 flight envelope, V3 rotor drag, V4 turn physics, V5 walking
rhythm, V6 tilt-acceleration link, V7 rotor vibration as an experiment). They are calibrated in the
healthy opening seconds, and a jamming meter sets the trust of each. No witness is load-bearing: V1 + V2
alone must bound drift; every other witness is behind a switch and stays on only if `score.py` shows a
gain on sequences we did not tune on. Full list and plan: `Docs/TRACK3_PLAN.md`.

The C core (`main.cpp`, step 9b) and its Dockerfile (`Dockerfile.ccore`) are a recorded experiment:
kept with their tests and results, never shipped or gated.

The S24 loader and live stations (`vortex/data/phone.py`, `vortex/stations.py`) and the ADVIO loader
are from the earlier direction: keep them working as jury-demo material, do not extend them. The old
ESP32 station code was deleted on 15 Nov 2026 (it remains in git history before that date).

Entrant: Arnav Jain (solo). Arnav works on Windows. Wants direct, concise answers; say plainly what was
not verified.

## Design rules

- A sensor failure changes trust (weights, covariance, the error bound); it never silently changes
  behaviour elsewhere.
- Estimators never see ground truth. Ground truth is used only for scoring and for the explicitly
  labelled "oracle" set-up of the dead-reckoning baseline.
- Primary metric: APE RMSE with SE(3) Umeyama fitted on the run being scored (what the organisers do),
  always beside the never-moving floor scored the same way; also RPE 1 s, error inside missing-row gaps
  and the blind 5 s. The older "given" alignment (fitted once on the clean run) is a diagnostic only.
- Every new feature is a switch, default off: built in the reference (`vortex/core`), then copied into
  `pathfinder.py` bit-identically. Its decision rule is committed before any on/off comparison on
  held-out data; it ships on only if it passes.
- Tuning: MH_01/02, TUM-VI room1/room2. Held out: MH_03..05, V1_01..03, room3/room4 (run once with the
  chosen values). **V2_01..03 is the final test set**: never read, fit or plot it until Arnav says "run
  the final table". The official script's seed is fixed at 42: tune on other seeds; seed 42 copies are
  for reporting only.
- Every fault run is reproducible from a seed. Every results table is generated by script.
- Conventions: quaternions Hamilton (w, x, y, z), body-to-world; gyro in body frame, rad/s; accel is
  specific force in m/s^2 (+g up at rest); timestamps in seconds.

## Working agreements

- Tests first, and run them (`pytest`). Report real pass/fail counts.
- Never fabricate numbers. Calibration-dependent values are named parameters with a source note.
  Synthetic results are labelled synthetic.
- Small commits on a feature branch, PR into `main`. Never force-push or rewrite `main`. One PR per step.
- Gates on every PR: pytest with exact counts; `check_output` PASS on every input; heap (tracemalloc)
  peak <= 4 MB (hard limit 8 MB); <= 50 us per row for `python -S main.py`; reference and
  `pathfinder.py` bit-identical; `Docs/BUDGET.md`, `Docs/RESULTS.md` and `Docs/TRACK3_PLAN.md` updated
  in the same commit. `main.py`/`pathfinder.py` stay pure Python (no numpy, no third-party imports).
- **Every PR gets a detailed description**: why the change exists; what changed in each file; tests run
  with exact counts and where; what was not checked; steps Arnav must run on Windows with the expected
  output; which rows of `Docs/TRACK3_PLAN.md` it updates.
- Ask before: deleting files, adding third-party dependencies, copying any third-party code (GPL code
  must not enter the repo without a decision), publishing anything. The organisers' `degrade_imu.py` is
  not committed until Arnav decides; it lives git-ignored in `tools/official/`.
- Third-party data and tools are listed in `THIRD_PARTY.md`. ADVIO is CC BY-NC 4.0 and never committed.
